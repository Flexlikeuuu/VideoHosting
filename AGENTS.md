# AGENTS.md — Правила разработки MVP видеохостинга (YouTube Clone)

## 1. Роли и контекст проекта
- **Пользователь:** Архитектор и ревьюер.
- **Агент:** Senior Fullstack & DevOps инженер.
- **Цель:** Создать production-ready MVP видеохостинга (аналог YouTube) с чистой слоистой архитектурой, надежной работой с медиа, строгими практиками информационной безопасности и деплоем на чистой Ubuntu одной командой.

---

## 2. Технологический стек (строго зафиксирован)
- **Backend:** Python 3.12+, FastAPI (async), SQLAlchemy 2.0 (`asyncpg`), Alembic, Pydantic v2.
- **БД и очереди:** PostgreSQL 16, Redis (очереди фоновых задач, кэширование, rate-limiting).
- **Object Storage:** MinIO (S3-совместимое хранилище) для хранения исходников, транскодированных видео и превью.
- **Медиа-обработка:** FFmpeg (извлечение метаданных, генерация превью/thumbnail, транскодирование в H.264/AAC MP4 с флагом `-movflags +faststart`) в асинхронном фоновом воркере (Arq на базе Redis).
- **Frontend:** React + TypeScript + Vite + Tailwind CSS (SPA с переключением темной/светлой темы, UX/UI максимально приближен к YouTube).
- **Инфраструктура:** Docker, Docker Compose, Nginx (единая точка входа: проксирование `/api`, `/docs`, отдача SPA-статики и стриминг видео с поддержкой `Range`-запросов).

---

## 3. Архитектурные стандарты
1. **Строгая слоистая архитектура бэкенда:**
   ```
   api/v1/routers  -->  services  -->  repositories  -->  models
   ```
   - **Routers (`api/v1/routers`):** только HTTP-слой (валидация входных Pydantic-схем, зависимости `Depends`, маппинг доменных исключений в HTTP-статусы, формирование ответов). **Запрещено:** бизнес-логика, прямые SQL-запросы, прямые вызовы S3/Redis.
   - **Services (`services`):** вся бизнес-логика, оркестрация репозиториев, проверка прав доступа (RBAC, ownership, private-доступ), постановка задач в очередь.
   - **Repositories (`repositories`):** инкапсуляция всех запросов к БД через SQLAlchemy 2.0 async session. Никакой бизнес-логики.
   - **Models (`models`):** декларативные модели SQLAlchemy 2.0, индексы, внешние ключи, enum-типы.
2. **Работа с видео и памятью:**
   - **Загрузка:** строго стриминговая передача (chunked streaming) в MinIO/S3 без вычитывания всего файла в RAM.
   - **Раздача:** обязательная поддержка HTTP `Range` (`Accept-Ranges: bytes`, статус `206 Partial Content`, корректные `Content-Range` и `Content-Length`).
3. **Документация API:**
   - Подробные docstrings у роутеров, `summary`, `description`, `responses` (описания кодов ошибок `400`, `401`, `403`, `404`, `409`, `413`, `415`, `429`), полные Pydantic v2 схемы с `Field(..., description=...)` и примерами для чистого Swagger (`/docs`).
4. **Качество кода и тестирование:**
   - Код без дублирования, с понятной типизацией (type hints), разделением ответственности и обработкой граничных случаев.
   - Автотесты (`pytest` + `httpx.AsyncClient`) для критичных сценариев: auth, RBAC, IDOR, upload validation, Range-стриминг, лайки/комментарии/подписки, модерация.

## 4. Стандарты информационной безопасности (ИБ)
- **Аутентификация:** JWT (`access_token` + `refresh_token`) в `httpOnly`, `SameSite=Lax` (и `Secure` в prod) cookies. Ротация refresh-токенов / защита от повторного использования.
- **Пароли:** хеширование через `Argon2` (или `bcrypt`) с безопасными параметрами; пароли никогда не логируются и не возвращаются в ответах.
- **RBAC:** роли `user`, `moderator`, `admin`. Проверка ролей через явные FastAPI dependencies.
- **Защита от IDOR:**
  - Строгая проверка владельца ресурса при изменении/удалении видео, комментариев, плейлистов.
  - Для `private` видео: доступ разрешен только владельцу, модератору/админу (при модерации/жалобе — по политике) или пользователям из явного списка доступа (access list / share grants). При отсутствии прав — `403 Forbidden` (или `404` для скрытия существования, согласованно по API).
- **Безопасность загрузок:**
  - Проверка реального MIME-типа и сигнатур файла (magic bytes, `ffprobe`/сигнатуры контейнеров MP4/WebM/MKV/MOV и изображений JPEG/PNG/WebP), а не только расширения или `Content-Type` от клиента.
  - Ограничение максимального размера файла, санитизация имен файлов (хранение в MinIO по UUID-ключам).
- **Rate-limiting:** ограничение частоты запросов (через Redis) на эндпоинты `/auth/*` (login, register, refresh) и `/videos/upload`.
- **Конфигурация:** никаких захардкоженных секретов в коде; все секреты через `.env` / переменные окружения (с шаблоном `.env.example`).

## 5. Протокол работы (Workflow)
1. **Итеративность и ревью:**
   - Разработка ведется строго по утвержденным этапам.
   - После завершения каждого этапа агент **останавливается**, запускает проверки (линтеры/тесты/сборку/smoke-проверку) в терминале, показывает реальный вывод и ждет ревью архитектора.
   - Переход к следующему этапу — только после подтверждения архитектора.
2. **Git-дисциплина:**
   - Каждый завершенный и проверенный этап фиксируется атомарным git-коммитом.
   - Формат сообщений — **Conventional Commits**: `feat:`, `fix:`, `chore:`, `docs:`, `test:`, `refactor:`.
   - Запрещено склеивать всю историю в один коммит или переписывать уже принятую историю.
3. **Точность отчетов:**
   - В отчетах указывать только реально проверенные файлы, команды и результаты тестов, которые были запущены после последних правок.
